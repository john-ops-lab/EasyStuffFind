# I-001 OpenClaw 照片未上传却确认成功

## 预期行为

飞书中的位置文字与随后发送的图片应关联到同一物品；OpenClaw 只有在
EasyStuffFind 二次查询确认 `photo_url` 非空后，才能回复照片已保存。

## 实际行为

物品位置成功写入，但照片元数据和照片文件均未新增。用户追问照片是否已挂上时，
OpenClaw 未调用工具便直接回复上传成功，Web 管理端因此显示空照片。

## 复现步骤

1. 先发送“物品放到某位置，图片如下”。
2. 下一条消息单独发送飞书图片。
3. 追问照片是否已挂上。
4. 检查服务请求日志、物品照片元数据与照片目录。

## 已确认事实

- 服务只收到物品 upsert，没有收到对应的 `PUT /items/{id}/photo`。
- 受影响物品的 `photo_filename`、`photo_content_type` 和 `photo_updated_at` 均为空。
- OpenClaw 的脱敏轨迹显示，错误确认所在轮次没有任何工具调用。
- 飞书原图仍在 OpenClaw 为该消息提供的暂存路径中，文件类型和大小有效。

## 主要假设

| 假设 | 验证方式 | 结果 |
|---|---|---|
| Web 缓存导致照片不显示 | 检查数据库、照片目录和服务日志 | 排除；照片从未上传 |
| API 上传后丢失元数据 | 检查上传请求与现有 API 集成测试 | 排除；没有上传请求 |
| Skill 未安装或对 agent 不可见 | 检查目标 agent 的 Skill 状态与安装文件 | 排除；Skill 可见且内容一致 |
| 分开发送文字和图片时流程约束不足 | 对照 Skill 与脱敏会话轨迹 | 确认 |

## 根因

原 Skill 只详细描述“图片和文字一起到达”的主路径，没有明确规定文字先发、图片后发
时的待关联状态，也没有规定用户追问时必须再次读取 API。模型因此跳过图片上传，并在
无工具证据时根据对话上下文错误确认成功。

## 修复

- Skill 增加文字先发、图片先发和图片单独到达三种顺序的确定流程。
- 明确使用当前提示中的 `[media attached: <path> (<mime>)]` 暂存路径，不分析图片，
  不通过目录时间猜测图片。
- 客户端新增 `verify-photo <item_id>`，照片不存在时返回非零退出码。
- `photo` 命令上传后自动执行第二次认证查询，只输出不含签名 URL 的验证结果。
- 明确禁止根据记忆或之前的承诺回答“照片挂上了吗”。
- 使用原消息对应的暂存文件补齐受影响物品照片，并完成 API 与 Web 双重验证。

## 验证证据

- 新增客户端回归测试在修复前稳定失败，修复后通过。
- 真实物品的 `verify-photo` 返回 `verified: true`。
- Web 管理端出现照片入口，大图加载完成，控制台无错误。
- 目标 agent 的已安装 Skill 与仓库版本一致，且 `eligible`、`modelVisible` 均为 true。

## 剩余风险

模型是否严格执行 Skill 仍属于真实 Agent 行为，需要下一次飞书“文字与图片分两条发送”
进行端到端复验。客户端和确认协议已经把可验证成功条件固定下来。

## 长期改进

把“未调用验证命令不得确认照片成功”保留为 Skill 的强制不变量，并在后续 OpenClaw
升级后重复一次真实飞书图片闭环。
